# POC Nginx — Plano de Implementação

> **Para workers agênticos:** REQUIRED SUB-SKILL: use
> superpowers:subagent-driven-development (recomendado) ou
> superpowers:executing-plans para implementar este plano tarefa a tarefa.
> Os passos usam sintaxe de checkbox (`- [ ]`) para acompanhamento.

**Goal:** Expor uma API NestJS containerizada à internet através de um Nginx
configurado manualmente numa VM Oracle Always Free, com o usuário escrevendo
cada configuração e Claude atuando como tutor.

**Architecture:** Quatro fases sequenciais numa VM `VM.Standard.E2.1.Micro`
(1 OCPU / 1 GB) com Ubuntu Server. A API roda em container Docker publicado
apenas no loopback (`127.0.0.1:8080`). O Nginx roda direto no host, sem
container, e é o único processo exposto à internet, na porta 80. O firewall é
aberto e validado enquanto o Nginx ainda serve conteúdo estático, de modo que
problemas de rede e problemas de proxy nunca sejam investigados ao mesmo tempo.

**Tech Stack:** Oracle Cloud Infrastructure (Always Free), Ubuntu Server,
Docker, NestJS (Node.js/TypeScript), Nginx, iptables.

**Spec:** [`docs/superpowers/specs/2026-09-07-poc-nginx-design.md`](../specs/2026-09-07-poc-nginx-design.md)

---

## Nota sobre o formato deste plano

Este plano desvia deliberadamente do formato padrão em dois pontos, porque o
produto aqui é aprendizado, não código entregue.

**1. Quem executa é uma pessoa, não um agente.** O usuário escreve todo o
código e roda todos os comandos. Claude explica, aponta a documentação oficial,
revisa e questiona. As Tarefas 2 a 7 são executadas pelo usuário; apenas a
Tarefa 1 é escrita por Claude.

**2. O plano não contém gabarito.** O formato padrão manda incluir o código
pronto em cada passo. Aqui isso destruiria o objetivo: um `nginx.conf` colado
do plano ensina zero. Então, para tudo que o usuário precisa escrever, o plano
especifica **comportamento exigido, referência oficial e comando de validação
com saída esperada** — nunca o conteúdo do arquivo.

Onde o conteúdo não é objeto de aprendizado — comandos de infraestrutura,
instalação de pacotes, configuração de swap — os comandos exatos aparecem
normalmente.

Cada tarefa termina com um checkpoint verificável por comando, seguido de uma
revisão conceitual: o usuário apresenta o que escreveu e Claude questiona as
escolhas antes de liberar a tarefa seguinte. Comando passando não fecha tarefa
sozinho.

## Global Constraints

Valores fixos, válidos para todas as tarefas. Copiados da spec.

- **Shape da instância:** `VM.Standard.E2.1.Micro` (1 OCPU / 1 GB RAM), Always Free
- **Sistema operacional da VM:** Ubuntu Server
- **Usuário SSH padrão da imagem Ubuntu na OCI:** `ubuntu`
- **Swap:** 2 GB em arquivo, criado antes do primeiro `docker build`
- **Porta interna da API:** `8080`
- **Porta pública:** `80`
- **Publicação do container:** `-p 127.0.0.1:8080:8080` — nunca `-p 8080:8080`
- **Bind do NestJS:** `app.listen(8080, '0.0.0.0')` — `app.listen(8080)` não funciona em container
- **Destino do `proxy_pass`:** `127.0.0.1:8080`
- **Headers obrigatórios no proxy:** `Host`, `X-Real-IP`, `X-Forwarded-For`
- **iptables:** regra nova sempre **inserida antes** da linha `REJECT` da chain `INPUT` (`iptables -I`), nunca acrescentada ao final (`iptables -A`)
- **iptables:** `ufw` não é usado em nenhuma etapa — a Oracle recomenda explicitamente contra nas imagens Ubuntu
- **iptables:** backup obrigatório antes de qualquer alteração, e teste sempre em uma segunda sessão SSH com a primeira aberta
- **Build da imagem:** acontece na VM, via `git clone`, não localmente
- **`curl` no Windows:** usar sempre `curl.exe`, nunca `curl`. No PowerShell, `curl` é alias de `Invoke-WebRequest`, que tem flags e saída diferentes e produz erros enganosos
- **Sem gabarito:** Claude não fornece conteúdo pronto de `nginx.conf`, `Dockerfile` ou código NestJS

- [ ] **Step 4: Escrever `docs/apostila/01-api-nestjs-docker.md`**

Conteúdo obrigatório:

- **Conceito:** o que o container isola em termos de rede — por que
  `localhost` dentro do container não é o `localhost` do host, e por que isso
  obriga o `app.listen` a usar `0.0.0.0`; o que `-p` faz de verdade (o Docker
  escreve regras na tabela `nat` do iptables, avaliadas **antes** da chain
  `INPUT`, o que significa que as suas regras de firewall não filtram portas
  publicadas por container); por que `-p 127.0.0.1:8080:8080` é a forma segura
  e `-p 8080:8080` expõe a API à internet sem passar pelo Nginx; o que um build
  multi-stage economiza e por que isso importa numa VM de 1 GB.
- **Referência oficial:** Dockerfile reference —
  https://docs.docker.com/reference/dockerfile/
- **Exercício:** os passos das Tarefas 3 e 4.
- **Como validar:** `curl localhost:8080/health` na VM.
- **Armadilhas:** `app.listen(8080)` sem `0.0.0.0`; `-p 8080:8080`;
  `npm install` sem swap.

Arquivo mais longo da apostila. Conteúdo obrigatório:

- **Conceito:** diretiva simples versus diretiva de bloco; os contextos `main`,
  `http`, `server`, `location` e o que cada um governa; como o Nginx escolhe o
  `location` de uma requisição; a diferença entre `nginx -s reload`,
  `nginx -s quit` e `nginx -s stop`, e como isso se relaciona com
  `systemctl reload nginx` no Ubuntu; por que `sites-available` e
  `sites-enabled` existem no Ubuntu e **não** aparecem na documentação do
  nginx.org — são convenção de empacotamento do Debian, não do Nginx upstream;
  as duas camadas de firewall e por que abrir uma só nunca funciona.
- **Referências oficiais:**
  - Beginner's Guide — https://nginx.org/en/docs/beginners_guide.html
  - Configuration File's Structure — https://nginx.org/en/docs/beginners_guide.html#conf_structure
  - Starting, Stopping, and Reloading — https://nginx.org/en/docs/beginners_guide.html#control
  - Serving Static Content — https://nginx.org/en/docs/beginners_guide.html#static
  - Best Practices for Your Compute Instances, seção "Essential Firewall Rules" — https://docs.oracle.com/en-us/iaas/Content/Compute/References/bestpracticescompute.htm
- **Exercício:** os passos das Tarefas 5 e 6.
- **Como validar:** `curl localhost` na VM e `curl.exe http://<ip>` no Windows.
- **Armadilhas:** o site default do Ubuntu já ocupa a porta 80; `iptables -A`

  acesso SSH; a regra não sobrevive a reboot sem `netfilter-persistent save`;

- [ ] **Step 6: Escrever `docs/apostila/02b-proxy-reverso.md`**

Conteúdo obrigatório:

- **Conceito:** o que um proxy reverso faz e como difere de um proxy comum;

  perde sem `proxy_set_header` e o que quebra quando isso acontece; a diferença

  aplicação atrás do proxy passa a ver `127.0.0.1` como origem de tudo se os

- **Referências oficiais:**
  - Setting Up a Simple Proxy Server — https://nginx.org/en/docs/beginners_guide.html#proxy

## Task 2: Provisionamento da VM na OCI

Executada pelo usuário. Material de apoio: `docs/apostila/00-provisionamento-oci.md`.

**Files:**
- Nenhum arquivo do repositório. O produto é a VM.

**Interfaces:**
- Consumes: nada
- Produces: o IP público da instância e o caminho da chave privada SSH, usados
  por todas as tarefas seguintes

- [ ] **Step 1: Gerar o par de chaves SSH no Windows**

```bash
ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\oci-poc-nginx
```

A chave privada fica em `oci-poc-nginx` e a pública em `oci-poc-nginx.pub`.
Nenhuma das duas entra no repositório.

- [ ] **Step 2: Criar a VCN**

No Console da OCI: **Networking → Virtual Cloud Networks → Create VCN**,
usando o assistente com conectividade à internet. Ele cria VCN, subnet pública,
subnet privada, Internet Gateway e as route tables.

Anotar o nome da subnet **pública** — a instância precisa ficar nela, e a
Tarefa 6 volta a essa subnet para editar a Security List.

- [ ] **Step 3: Criar a instância**

**Compute → Instances → Create Instance**, com:
- Image: Ubuntu Server
- Shape: `VM.Standard.E2.1.Micro` (marcado como Always Free eligible)
- Networking: a VCN criada e a subnet **pública**
- Assign a public IPv4 address: **sim**
- SSH keys: colar o conteúdo de `oci-poc-nginx.pub`

Anotar o IP público atribuído.

- [ ] **Step 4: Primeiro acesso SSH — deve funcionar antes de qualquer outra coisa**

```bash
ssh -i $env:USERPROFILE\.ssh\oci-poc-nginx ubuntu@<ip-publico>
```

Esperado: shell da VM. A porta 22 já vem liberada por padrão, tanto na Security
List quanto no iptables. Se este passo falhar, parar e resolver antes de
continuar — a partir daqui, SSH é o único acesso à máquina.

- [ ] **Step 5: Confirmar que ainda não existe swap**

```bash
free -h
```

Esperado: linha `Swap` zerada. Este é o estado "antes"; o passo seguinte muda
isso.

- [ ] **Step 6: Criar 2 GB de swap**

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

A última linha faz o swap sobreviver a reboot.

- [ ] **Step 7: Validar o swap**

```bash
free -h
```

Esperado: linha `Swap` com aproximadamente `2.0Gi` no total.

- [ ] **Step 8: Instalar git, curl e Docker**

```bash
sudo apt update
sudo apt install -y git curl
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker ubuntu
```

Referência oficial: https://docs.docker.com/engine/install/ubuntu/

- [ ] **Step 9: Reconectar para o grupo `docker` valer**

Sair da sessão SSH e entrar de novo. A adição ao grupo só vale em sessão nova.

- [ ] **Step 10: Validar o Docker sem `sudo`**

```bash
docker run hello-world
```

Esperado: a mensagem "Hello from Docker!". Se pedir permissão, a reconexão do
passo anterior não aconteceu.

- [ ] **Step 11: Revisão conceitual**

Apresentar a Claude: qual a diferença entre a subnet pública e a privada, e o
que aconteceria se a instância tivesse sido criada na privada.

## Task 5: Nginx servindo conteúdo estático

Executada pelo usuário, na VM. Material de apoio:
`docs/apostila/02a-nginx-estatico-e-rede.md`. Nenhum firewall é tocado nesta
tarefa — validação apenas local.

**Files:**
- Create: `/var/www/poc-api/index.html` (na VM)
- Create: `/etc/nginx/sites-available/poc-api` (na VM)
- Create: `nginx/poc-api.conf` (cópia versionada no repositório)

**Interfaces:**
- Consumes: a VM da Tarefa 2
- Produces: um `server` block escutando na porta 80, servindo estático. A
  Tarefa 6 valida a rede contra ele; a Tarefa 7 substitui o corpo do `location`
  por `proxy_pass`.

- [ ] **Step 1: Instalar o Nginx**

```bash
sudo apt install -y nginx
```

- [ ] **Step 2: Ver o que o pacote já colocou no ar**

```bash

```

Esperado: a página "Welcome to nginx!". Ela vem do site default do Ubuntu, que
já ocupa a porta 80 — é o que o próximo passo remove.

- [ ] **Step 3: Desabilitar o site default**

```bash

sudo systemctl reload nginx
curl localhost
```

Esperado: erro de conexão ou resposta vazia. A porta 80 está livre.

O arquivo continua em `sites-available` — só o symlink em `sites-enabled` foi
removido. Entender essa distinção é parte do exercício.

- [ ] **Step 4: Criar a página estática**

```bash

```

- [ ] **Step 5: Escrever o `server` block**

Criar `/etc/nginx/sites-available/poc-api`. Comportamento exigido:
- escuta na porta 80
- serve `/var/www/poc-api` como raiz
- `/` entrega o `index.html`

Copiar o conteúdo de `/etc/nginx/sites-available/poc-api` para

## Task 6: Abrir a porta 80 nas duas camadas de firewall

Executada pelo usuário. Material de apoio:
`docs/apostila/02a-nginx-estatico-e-rede.md`.

> **Atenção — risco de perda permanente de acesso à VM.** Esta tarefa altera as
> regras de firewall que também governam o SSH. Um erro aqui derruba a conexão
> e a instância fica inacessível: não há "desfazer", e a recuperação exige
> console serial da OCI ou recriar a instância do zero. Os Steps 4, 5 e 8
> existem especificamente para tornar qualquer erro reversível. Nenhum deles é
> opcional.

**Files:**
- Modify: Security List da subnet pública (Console OCI)
- Modify: `/etc/iptables/rules.v4` na VM, via `netfilter-persistent`

**Interfaces:**
- Consumes: o Nginx servindo estático da Tarefa 5
- Produces: porta 80 alcançável da internet. A Tarefa 7 assume rede resolvida
  e não volta a mexer em firewall.

- [ ] **Step 1: Confirmar o estado "antes"**

No Windows:

```bash
curl.exe --max-time 10 http://<ip-publico>
```

Esperado: timeout. Mesmo resultado do Step 8 da tarefa anterior — ponto de
partida registrado.

- [ ] **Step 2: Adicionar a regra de Ingress na Security List**

No Console da OCI: **Compute → Instances → sua instância → link da subnet →
Security List associada → Add Ingress Rules**.

- Source Type: `CIDR`
- Source CIDR: `0.0.0.0/0`
- IP Protocol: `TCP`
- Source Port Range: `All`
- Destination Port Range: `80`

Referência oficial:
https://docs.oracle.com/en-us/iaas/Content/Network/Concepts/securitylists.htm

- [ ] **Step 3: Testar de novo — ainda deve falhar**

```bash
curl.exe --max-time 10 http://<ip-publico>
```

Esperado: **ainda timeout**. Este resultado não é um erro seu: a segunda camada
de firewall, dentro da VM, continua bloqueando. É aqui que a maioria dos
iniciantes conclui que a Security List não funcionou e começa a mexer no lugar
errado.

- [ ] **Step 4: Backup das regras atuais**

Na VM:

```bash
sudo iptables-save > ~/iptables.backup
```

- [ ] **Step 5: Abrir uma segunda sessão SSH e deixá-la aberta**

Em outro terminal do Windows, conectar de novo na VM. Manter **as duas** abertas
até o fim da tarefa. Se a alteração quebrar o acesso, uma sessão já
estabelecida continua funcionando e permite restaurar o backup.

- [ ] **Step 6: Localizar a linha `REJECT` da chain `INPUT`**

```bash
sudo iptables -L INPUT --line-numbers
```

Anotar o número da linha `REJECT`. A regra da porta 80 precisa entrar **antes**
dela. `iptables -A INPUT` acrescenta ao final, depois do `REJECT`, e não tem
efeito nenhum — a regra aparece listada e o comportamento não muda. Esse é o
erro mais comum desta etapa, e o mais difícil de diagnosticar justamente porque
`iptables -L` mostra a regra lá.

Confirmar também qual linha libera a porta 22. Ela não pode ser alterada,
removida, nem passar para depois do `REJECT`.

- [ ] **Step 7: Inserir a regra antes do `REJECT`**

Substituindo `<N>` pelo número da linha do `REJECT`:

```bash
sudo iptables -I INPUT <N> -m state --state NEW -p tcp --dport 80 -j ACCEPT
```

- [ ] **Step 8: Verificar o SSH antes de qualquer outra coisa**

Abrir uma **terceira** sessão SSH. Se conectar, o acesso está preservado. Se
não conectar, restaurar imediatamente pela sessão que ainda está aberta:

```bash
sudo iptables-restore < ~/iptables.backup
```

- [ ] **Step 9: Validar o acesso externo**

No Windows:

```bash
curl.exe http://<ip-publico>
```

Esperado: o conteúdo do `index.html` da Tarefa 5. **Rede provada.** A partir
daqui, qualquer falha de acesso externo é problema de configuração do Nginx,
não de firewall.

- [ ] **Step 10: Persistir a regra**

```bash
sudo netfilter-persistent save
```

Sem isso, a regra desaparece no próximo reboot e a POC "para de funcionar
sozinha".

- [ ] **Step 11: Confirmar a persistência**

```bash
sudo reboot
```

Reconectar depois de alguns minutos e repetir o Step 9. Esperado: mesmo
resultado. Confirmar também que o container voltou sozinho:

```bash
docker ps
curl localhost:8080/health
```

O `--restart unless-stopped` da Tarefa 4 é o que faz isso acontecer.

- [ ] **Step 12: Revisão conceitual**

Apresentar a Claude a saída de `sudo iptables -L INPUT --line-numbers`.
Perguntas a responder: por que a ordem das regras importa; o que teria
acontecido com `-A` no lugar de `-I`; por que a Oracle desaconselha `ufw` nestas
imagens.

## Task 7: Proxy reverso

Executada pelo usuário, na VM. Material de apoio:
`docs/apostila/02b-proxy-reverso.md`. Última tarefa do plano.

**Files:**
- Modify: `/etc/nginx/sites-available/poc-api` (na VM)
- Modify: `nginx/poc-api.conf` (cópia versionada)

**Interfaces:**
- Consumes: o container em `127.0.0.1:8080` da Tarefa 4; o `server` block da
  Tarefa 5; a rede provada da Tarefa 6
- Produces: a API acessível pela internet através do Nginx — objetivo final da
  POC

- [ ] **Step 1: Confirmar o estado "antes"**

No Windows:

```bash
curl.exe http://<ip-publico>/health
```

Esperado: 404 do Nginx. O caminho `/health` não existe como arquivo estático em
`/var/www/poc-api`. O Nginx está respondendo — só não sabe encaminhar ainda.

- [ ] **Step 2: Trocar o estático por `proxy_pass`**

Editar `/etc/nginx/sites-available/poc-api`. Comportamento exigido:
- as requisições deixam de ser servidas do disco e passam a ser encaminhadas
  para `127.0.0.1:8080`
- as diretivas de conteúdo estático saem

Referência oficial: https://nginx.org/en/docs/beginners_guide.html#proxy

- [ ] **Step 3: Testar a sintaxe e recarregar**

```bash
sudo nginx -t
sudo systemctl reload nginx
```

- [ ] **Step 4: Validar de dentro da VM**

```bash
curl localhost/health
```

Esperado: o JSON da API — o mesmo de `curl localhost:8080/health`, agora
atravessando o Nginx na porta 80.

- [ ] **Step 5: Validar de fora**

No Windows:

```bash
curl.exe http://<ip-publico>/health
curl.exe http://<ip-publico>/info
```

Esperado: os dois JSONs da Tarefa 3, Step 1. **Objetivo da POC cumprido.**

- [ ] **Step 6: Observar a informação que se perdeu**

```bash
docker logs poc-api --tail 20
```

Esperado neste momento: a origem das requisições aparece como `127.0.0.1` — o
próprio Nginx. Do ponto de vista da API, todo o tráfego do mundo vem do
loopback. O IP real de quem chamou foi perdido no encaminhamento. Este é o
problema que o próximo passo corrige.

- [ ] **Step 7: Adicionar os headers de encaminhamento**

Comportamento exigido no mesmo `location`:
- `Host` repassa o host original da requisição
- `X-Real-IP` repassa o IP do cliente
- `X-Forwarded-For` acumula a cadeia de proxies

Referência oficial, diretiva `proxy_set_header`:
https://nginx.org/en/docs/http/ngx_http_proxy_module.html

- [ ] **Step 8: Recarregar e validar os headers**

```bash
sudo nginx -t
sudo systemctl reload nginx
```

No Windows, gerar tráfego novo:

```bash
curl.exe http://<ip-publico>/health
```

Na VM:

```bash
docker logs poc-api --tail 5
```

Esperado: o IP público da sua conexão no Windows, não `127.0.0.1`. Se ainda
aparecer loopback, os headers não estão sendo aplicados — o proxy funciona e a
informação continua se perdendo, que é a falha silenciosa desta etapa.

- [ ] **Step 9: Atualizar a cópia versionada e commitar**

```bash
git add nginx/poc-api.conf
git commit -m "feat: proxy reverso para a API com headers de encaminhamento"
git push
```

- [ ] **Step 10: Revisão conceitual final**

Apresentar a Claude o `nginx.conf` completo. Perguntas a responder: o que muda
com e sem a barra final no `proxy_pass`; qual a diferença entre `X-Real-IP` e
`X-Forwarded-For` e por que os dois existem; por que a API não pode ser
alcançada diretamente na porta 8080 de fora, e qual configuração garante isso;
quais das duas camadas de firewall precisariam mudar para expor HTTPS na porta
443.
